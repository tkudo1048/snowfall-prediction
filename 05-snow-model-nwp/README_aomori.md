# 【青森を対象にした結果】数値予報モデルの値（上空の寒気など）を足すと、翌日の青森の降雪量・大雪日はどれだけ当たるようになるか

このファイルは、目的変数を「翌日の青森の降雪量」にしたときの記録（2026-10-18 実行）。いまのフォルダの既定の対象は弘前で、弘前の結果は `README.md`。
青森の結果・図・ログは `results/aomori/`、`images/aomori/`、`logs/aomori/` にある。スクリプトは `--target aomori` を付けると青森を対象に動く。
フォルダの移動（`05-snow-model-nwp/`）と、対象地点の切り替えのためのコード変更の後も、青森のデータセット（特徴量・目的変数）が変わらないことを確かめた。

青森・弘前の日別観測（気象庁）に、気象庁の数値予報モデル（GSM・MSM）の値を特徴量として足し、翌日の青森の日降雪量(cm)と大雪日（翌日20cm以上）を予測した。
特徴量は3セット（S0・SA・SB）を用意し、それぞれ同じ手順・同じ試行数でチューニングして比べた。

- S0（基準）: 観測だけ。前回の `04-snow-model/` と同じ特徴量（期間を2016年からに広げた）。
- SA（運用可能）: S0 ＋ 今日（t日）の数値予報の値。今日の21時までの値だけを使う。
  GSM は補間されていない6時間ごとの本来の値（03・09・15・21時）だけを使う（後述「数値予報の補間とリーク対策」）。
  t日21時より後の数値予報の生データ・補間値を使っていないことを `test_no_leak.py` で確かめた。
- SB（上限の目安・運用不可）: SA ＋ 明日（t+1日）の数値予報の値。「明日の予報が実況並みに当たった場合」の上限。
  実際の運用ではこの精度は出ない。結果も運用の精度（SA）と混ぜて読まないこと。

この README の数字は、GSM の補間値の問題を直した後（2026-10-18 実行）のもの。修正前の結果は `results_v1_before_fix/` に残しているが、補間値を使っていたので記事には使わない。

## 結論（評価データ = 2024年・2025年の冬、301日、大雪日16日）

### 運用できる形（SA: 今日までの数値予報を足す）

- 降雪量の平均誤差（MAE）は、S0 から 0.07〜0.17cm（2〜5%）小さくなった（手法により3.39〜3.52cm → 3.23〜3.45cm）。
  - 3つの seed すべてで小さくなる向きだった。
  - 95%区間（7日ブロック）が0をまたがないのは、3手法のうち勾配ブースティング（−0.165cm、−0.333〜−0.006cm）とランダムフォレスト（−0.158cm、−0.273〜−0.039cm）の2つ。Ridge回帰（−0.071cm）は0をまたぐ。
    3手法を並べて比べた中での結果で、多重比較の補正はしていない。勾配ブースティングの区間の上端は −0.006cm で、0にかなり近い。
  - 持続予測（翌日も今日と同じ）よりは、どの手法も0.62〜0.85cm小さく、区間は0をまたがない。
- 大雪日（翌日20cm以上）は、相変わらずほぼ当たらない。
  - 予測値20cm以上を「大雪」とすると、S0・SA ともに16日中0日（全手法）。SA の予測の最大は11.6〜15.9cm。
  - 判定の線を下げる（CVで決めた4.8〜6.7cm）と、SA は16日中8〜10日を拾えるが、「大雪」と出した日が40〜52日あり、当たりは17〜23%。持続予測（13cm以上で大雪、45日中8日的中）と大きくは変わらない。
  - 大雪日専用の分類モデルは、ロジスティック回帰を主に読む（勾配ブースティング分類は確率の較正をしておらず、判定の線が不安定なため。後述）。
    SA のロジスティック回帰の AP は 0.327（S0 は 0.259）。差 +0.068 の95%区間は −0.067〜+0.185 で0をまたぐ。CV の AP は S0 0.110、SA 0.103 でほぼ同じ。
- SA のモデルが数値予報から一番使っていたのは「今日21時の500hPa高度（上空5,500m付近の気圧の谷の深さ）」と「上流（日本海）の21時の850hPa気温（上空1,500m付近の寒気）」だった。

### 運用できない上限（SB: 明日の数値予報が実況並みに当たったとしたら）

- MAE は 2.21〜2.74cm。SA から 0.71〜1.05cm 小さく、95%区間は0をまたがない。
- 大雪日の AP は 0.49〜0.73（分類モデルと、回帰の予測値で判定した場合）。ただし予測値20cm以上の判定では、SB でも16日中0〜1日。
- この改善のほとんどは「明日のMSMの降雪量」そのものから来ている。
  - MSMの降雪量に倍率1.55を掛けただけの予測で MAE 2.45cm。SB の勾配ブースティング（2.21cm）・ランダムフォレスト（2.25cm）とほぼ同じで、SB の Ridge回帰（2.74cm）より小さい。
  - 大雪日の AUC は MSMの降雪量そのままで 0.974、SB の分類モデルは 0.919〜0.956。

### ひとことで

今日までの数値予報（上空の寒気・気圧の谷）を足しても、翌日の降雪量の誤差（MAE）は2〜5%しか減らず、大雪日もほぼ当たらないままだった。
大きく当たるようになるのは「明日の予報」を使った場合だが、それはこのデータでは実況に近い値で代用しているので、運用ではここまで出ない。

## 用語のかみくだき（記事に転記する用）

- 数値予報モデル: 大気の動きを物理の式で計算して、未来の天気を出すコンピュータのモデル。気象庁の GSM（地球全体を計算するモデル）と MSM（日本付近を細かく計算するモデル）を使った。
  今回 Open-Meteo から取得できたのは、GSM が0.5度格子（南北約55km・東西約42km）・6時間ごと、MSM が約5km格子・1時間ごと。
- 850hPa・700hPa・500hPa: 上空の高さの目安。850hPa ≒ 1,500m、700hPa ≒ 3,000m、500hPa ≒ 5,500m。「850hPaで −6℃以下なら平地でも雪」が目安。
- 500hPa高度: 500hPaになる高さ。低いところは「気圧の谷」で、寒気が入りやすい。
- 補間: 6時間おきにしかない値の間を、前後の値からなめらかにつないで1時間ごとの値を作ること。間の値を作るのに「後ろ（未来）の値」も使うので、予測に使うと未来の情報が混ざる。
- MAE（平均絶対誤差）: 予測と実際の差（cm）を平均したもの。小さいほど良い。
- AUC: 大雪日とそれ以外の日を、点数の高い順にどれだけ正しく並べられるか。0.5 = でたらめ、1 = 完ぺき。
- average precision（AP）: 「大雪」と言った日がどれだけ当たっていたかを、判定の線をいろいろ変えて平均したもの。大雪日が少ないときに AUC より厳しめに出る。でたらめに言うと大雪日の割合（評価データでは0.053）くらいになる。
- 適合率: 「大雪」と言った日のうち、本当に大雪だった割合。再現率: 本当の大雪日のうち、「大雪」と言えた割合。
- 過学習: 学習に使ったデータには良く当てはまるのに、新しいデータでは当たらなくなること。学習データでの成績とCV・評価での成績の差（ギャップ）で見る。
- permutation importance: ある特徴量（の組）の値を日付の間でシャッフルして、精度がどれだけ落ちるかを見る方法。大きく落ちる特徴量ほど、モデルが頼っている。
- ブートストラップ: 評価データの日を選び直して何千回も計算し直し、「たまたまの差」かどうかの幅（95%区間）を見る方法。7日ブロック版は、連続する7日をひとかたまりで選び直す（天気は数日続くため）。

### 数値予報（Open-Meteo Historical Forecast API）

- 出典: Open-Meteo（https://open-meteo.com/）。元データは気象庁 GSM・MSM。ライセンスは CC BY 4.0（非商用利用の範囲で使用）。
- 保存先: `data/openmeteo/`（API応答のJSONそのまま。66ファイル）と呼び出し記録 `api_calls.log`。
- 取得期間: 2016-01-01〜2016-04-01、および各冬の 10/25〜翌4/1（2016〜2025年の冬）。計11期間。
- 地点（括弧内はAPIが返した格子点）:
  - 青森 40.82N 140.77E（GSM: 41.0N 141.0E、MSM: 40.8N 140.75E）
  - 上流・西 40.5N 139.5E（日本海、男鹿半島の北。GSM・MSMとも 40.5N 139.5E）
  - 上流・北西 41.3N 139.9E（日本海、津軽半島の西。GSM: 41.5N 140.0E、MSM: 41.3N 139.875E）
  - GSM の格子は0.5度で粗い。青森の GSM 格子点は陸奥湾〜下北寄り。
- 変数（毎時で返ってくる）:
  - 青森 GSM: 850hPaの気温・相対湿度・風速・風向、700hPaの相対湿度、500hPaの気温・高度、地上の気温・降水量・降雪量・海面気圧
  - 青森 MSM: 地上の気温・降水量・降雪量・海面気圧（MSMは API 上で上空の値が null のため）
  - 上流2点 GSM: 850hPaの気温・相対湿度・風速・風向、700hPaの相対湿度、降水量。MSM: 降水量
- API呼び出し: 本取得66回（すべて成功、2026-10-17 14:24〜14:33、間隔6秒）＋事前の動作確認1回 = 67回。再実行時は保存済みファイルを使い、通信しない。
  1回あたり最大11変数・約160日分。Open-Meteo の「10変数・14日を1回と数える」換算では、本取得で約734回分の見積もり（無料枠 1日10,000回）。
- 欠損: 2016-01-01 の0〜9時（APIが値を返さない。瞬間値は0〜8時の9時間、降水量・降雪量は9時までの10時間分。全地点・全モデル共通）。そのため 2016-01-01 の t日の数値予報の特徴量のうち20列が欠損（1行）。取得した期間の中で、それ以外の欠損はない。

- Open-Meteo の降雪量は降水量と気温から換算した値（GSMは6時間、MSMは1時間ごとの降水量 × 0.7cm/mm。気温が低いときだけ）で、気象庁の観測の降雪量より小さく出る（学習・評価データ全体の1日あたり平均で 1.44cm 対 3.62cm）。

### 数値予報の補間とリーク対策

API は GSM の値も「1時間ごと」で返すが、GSM のモデル本来の値は 03・09・15・21時JST（00・06・12・18 UTC）の6時間ごとしかない。それ以外の時刻は、Open-Meteo が前後の本来の値から補間（Catmull-Rom 補間）した値だった。

- 確かめ方（`check_gsm_native_hours.py`、結果は `logs/check_gsm_native_hours.log`）:
  - 「どの時刻を本来の値とみなすと、残りの時刻を補間でいちばん正確に再現できるか」を全候補で比べた。GSM の上空・地上の瞬間値（気温・湿度・高度・気圧）は、どれも「03・09・15・21時」で誤差が丸め誤差程度（850hPa気温で平均0.04℃）になった。
  - GSM の t日16〜20時の850hPa気温を、t日09・15・21時と t+1日03時の値で回帰すると、t+1日03時の係数は 16時 −0.012、17時 −0.038、18時 −0.063、19時 −0.073、20時 −0.057。Catmull-Rom 補間の理論値（−0.012、−0.037、−0.062、−0.074、−0.058）と一致した。
    → t日16〜20時の値には、翌日03時（予測する時点より後）の値が混ざっている。
  - MSM は補間の誤差が丸め誤差よりずっと大きく（地上気温で平均0.23℃）、1時間ごとが本来の値と判断した。
  - GSM の降水量・降雪量は「03〜09時」「09〜15時」「15〜21時」「21〜翌03時」の6時間の合計を6等分した値。降雪の有無は、かたまりの終わり（例: 21時）の地上気温で99.6%説明できた。かたまりの外の値は混ざっていない。
- 修正前（`results_v1_before_fix/`）は、GSM の「t日0〜21時の毎時の平均・最低」を使っていたため、t日16〜20時の補間値（= t+1日03時の値が −1〜−7% の重みで混ざった値）が SA の10列に入っていた。
  対象: nt_t850_mean, nt_rh850_mean, nt_rh700_mean, nt_t500_mean, nt_z500_mean, nt_u850_mean, nt_v850_mean, nt_ws850_mean, nt_stab_mean, nt_t850_min。
  SB の t+1日の値（日平均）と上流点の日平均も、同じように補間値（t+2日03時の値が混ざる）を使っていた。
- 修正後（いまの `common.py`）:
  - GSM の瞬間値は、読み込んだ直後に 03・09・15・21時以外を欠損にし、その4時刻の値だけで平均・最低を計算する（SA・SB・上流点すべて）。21時の値・「21時 − 9時」の変化はもともと本来の値。
  - GSM の降水量・降雪量は、SA・SB とも「その日の0〜21時」の合計（6時間のかたまりの終わりが21時まで）。修正前の SB は0〜24時の合計で、t+2日03時に終わるかたまりの一部が入っていたので、これもやめた。
  - MSM は1時間ごとの本来の値なので、SA は t日0〜21時、SB は t+1日0〜24時の値をそのまま使う。
- テスト（`test_no_leak.py`、結果は `logs/aomori/test_no_leak.log`、すべて通過）:
  1. 27日分（最初の日・最後の日を含む）について、t日21時より後の生データを全地点・全モデルででたらめな値・欠損に書き換えても、SA の数値予報の特徴量（47列）は1セルも変わらない。
  2. GSM の補間された時刻（03・09・15・21時以外）の値を全期間で書き換えても、t日・t+1日の数値予報の特徴量（79列 × 全日）は1セルも変わらない（= 16〜20時の補間値を使っていない）。
  3. SB の t+1日の値は、GSM の t+1日21時より後・MSM の t+1日24時より後を書き換えても変わらない。
  4. 確認の確認: t日21時の値を書き換えると特徴量は変わる（テストが変化を見逃さない）。
  5. 修正前のやり方に戻すと、2. のテストで上の10列が変わる（= 修正前は補間値を使っていた）。
- 修正の影響は小さかった（後述「修正前との比較」）。SA の MAE は修正前とほぼ同じか少し小さくなり、補間値のリークが成績を押し上げていた様子はなかった。

## 設計

- 目的変数: 翌日(t+1)の青森の日降雪量(cm)（気象庁の観測）。予測対象日が11〜3月の日だけを使う。
- 冬の決め方: 予測対象日が11〜12月ならその年、1〜3月なら前年の冬（例: 2025-11〜2026-03 = 2025年の冬）。
- 学習データ: 2015年の冬（2016-01-02〜03-31 のみ）〜2023年の冬（〜2024-03-31）。1,299日、大雪日36日。
- 評価データ: 2024年の冬（150日、大雪日9日）と2025年の冬（151日、大雪日7日）。
  - 評価データは、修正前のモデルで2回（同じモデルなので数字は同じ）、レビューでの感度確認で1回（翌日03時の寄与を除いても評価MAEの差は ±0.004cm）、修正後に1回見ている。修正はコードの点検（補間の仕組み）から決めたもので、評価データの結果を見て特徴量・手法・パラメータを選んだことはない。ただし修正の判断は、感度確認の結果（影響はほぼ0）を知ったうえで行った。
- チューニング: 学習データ内の冬単位の前向きCV。検証 = 2019〜2023年の冬（5分割）で、各冬をそれより前の冬すべてで学習して予測。
  - 回帰: 5つの検証冬の MAE の平均を最小化。
  - 大雪の分類: 5つの検証冬の予測をまとめて1つの AP を計算し、最大化（大雪日が1日しかない冬があるため）。
  - Optuna（TPESampler）で各「特徴量セット×手法×seed」100試行。seed は 42（主結果）・7・2024。
- 手法:
  - 回帰: Ridge回帰（線形）、勾配ブースティング（HistGradientBoosting）、ランダムフォレスト。探索範囲は前回と同じ。「目的変数を log1p 変換するか」を全手法で同じ選択肢として探索。予測の0未満は0に切る。
  - 大雪の分類: ロジスティック回帰、勾配ブースティング分類。クラス重み（大雪日1日をふつうの日の何日分とみなすか、1〜50倍）も探索。確率の較正（キャリブレーション）はしていない。
- 大雪の判定の線: 学習データのCV予測で F1（適合率と再現率のバランス）が最大になる値を決め、評価データにそのまま当てた。回帰では「予測値20cm以上」の判定も出した。

### 特徴量

- S0（51項目）: 前回 `04-snow-model/README.md` の特徴量から弘前の湿度2項目を除いたもの。観測は t日の日別値（t日24時まで）。
- SA（98項目）= S0 ＋ t日の数値予報（47項目、名前は `nt_`）。
  - 青森（GSM上空）: 850hPa気温・相対湿度・東西風・南北風・風速、700hPa相対湿度、500hPa気温・高度の「t日03・09・15・21時の4回の平均」と「21時の値」、850hPa気温の4回の最低
  - 850hPaと500hPaの気温差（大きいほど対流が起きやすい）の4回の平均と21時、t日中の変化（21時 − 9時）: 850hPa気温・500hPa高度・海面気圧(MSM)
  - 寒気の折れ線: max(0, −6℃ − 21時の850hPa気温)、それ×850hPa湿度
  - 青森（地上）: MSM気温（0〜21時の平均・21時）、MSM・GSMの降水量と降雪量の0〜21時の合計、MSM海面気圧（0〜21時の平均・21時）、地上気温(MSM) − 850hPa気温（21時）
  - 上流2点: 21時の850hPa気温・相対湿度・東西風・南北風、700hPa相対湿度、GSM・MSMの降水量の0〜21時の合計
- SB（130項目）= SA ＋ t+1日の数値予報（32項目、名前は `n1_`）。GSM は t+1日03・09・15・21時の平均・最低と0〜21時の降水・降雪の合計、MSM は t+1日0〜24時の平均・合計。

### リーク対策のまとめ

- 観測は t日以前の値だけ（前回と同じ）。t日の夜の天気概況は使わない。
- SA の数値予報は t日21時までの値だけ。GSM は補間されていない本来の値だけ（上の節とテストを参照）。
- 予測は「t日の夜〜深夜」に行う想定。
- SB の t+1日の値は、運用では手に入らない（予報なら手に入るが、ここで使ったのは実況に近い値）。上限の目安としてだけ扱う。
- 中央値での穴埋め・標準化・月別平均・MSM降雪量の倍率は、学習に使う範囲のデータだけで計算した。

## 限界・注意（記事で必ず添える）

- SB は運用できない。t+1日の数値予報の値は、Open-Meteo Historical Forecast API の「ほぼ実況」の値で、前日に出た予報ではない。本物の前日予報は外れることがあるので、SB の精度は「上限の目安」。MSMの降雪量をそのまま使った参考値も同じ理由で運用の精度ではない。
- SA も少し楽観的な可能性がある。
  - t日21時の GSM の値は、21時（12 UTC）の解析値に近い値と考えられる。解析には21時の前後数時間（〜24時ごろまで）の観測が取り込まれている可能性がある。
  - 運用でその値が手に入るのは、計算の時間を含めて深夜（日付が変わるころ以降）になる。t日21時の値で「t日の夜に予測する」というのは、実際より少し早い時点を想定している。
  - どちらも予測対象日（t+1日）の値ではないので目的変数の答えそのものは入らないが、「t日の夜の時点で手に入る情報」よりは少し新しい情報を使っている可能性がある。
- 評価データの大雪日は16日（2冬）だけ。AP・AUC・的中日数の差は、95%区間が広い（たとえば SA − S0 のロジスティック回帰の AP の区間は −0.07〜+0.19）。1〜2日の当たり外れで数字が大きく動く。
- SA − S0 の MAE で区間が0をまたがなかったのは、3手法を並べた中の2つ（勾配ブースティング・ランダムフォレスト）。多重比較の補正はしておらず、勾配ブースティングの区間の上端は −0.006cm で0に近い。
- CVスコアは100試行の中の最良値なので、楽観的（選んだ分だけ良く見える）。評価MAE は CV MAE より大きいが、主な理由は評価の2冬の雪が多かったこと。「常に0」比では CV と評価が近い（上の「過学習のギャップ」）。
- 評価データは、修正前のモデルで2回、レビューでの感度確認で1回、修正後に1回見ている（詳しくは「分割」）。修正の中身はコードの点検で決め、評価の結果では選んでいない。
- 勾配ブースティング・ランダムフォレストは学習データへの当てはまりと CV・評価の差が大きい（過学習のギャップ）。勾配ブースティング分類は学習データで AP 1.000。
- 勾配ブースティング分類は確率の較正をしていない。判定の線（CVで決定）が、学習データ全体で学習し直したモデルの確率とずれやすく、的中数が seed や修正の前後で大きく動く（SA で 2日 → 4日）。分類の結論はロジスティック回帰を主にして読む。
- ロジスティック回帰のクラス重み（大雪日の重み）は、本番の探索（1〜50倍）で S0 は seed によって範囲の両端に分かれた（seed 42: 49.2倍、seed 2024: 49.6倍は上限付近、seed 7: 1.0倍は下限）、SA は 36.8〜48.3倍が選ばれた。
  CVだけで上限を500倍に広げて試すと、選ばれたのは S0 489倍、SA 373倍と、やはり範囲の上のほう（S0 は上限に張りついたまま）だった。CV AP は S0 0.110 → 0.127、SA 0.103 → 0.107、SB 0.304 → 0.305 で、差は小さい（`check_logreg_weight_range.py`、`logs/aomori/check_logreg_weight_range.log`）。重みの範囲を広げても結論は変わらないと判断したが、最適な重みは見つけきれていない。
- GSM の格子は0.5度と粗く、青森の格子点は陸奥湾〜下北寄り（41.0N 141.0E）。GSMの降雪量そのままの成績が悪い（評価 AUC 0.674）のは、この粗さも一因と考えられる。
- 2016〜2026年の間に気象庁のモデルは何度か改良されている。値のくせが年によって変わっている可能性は確認していない。
- 弘前の湿度は2021年3月以前に観測がないため除いた。前回（5冬・1冬評価）とは学習期間・評価期間が違うので、S0 の数字は前回の README の数字とは一致しない（前回の評価冬と同じ2025年の冬だけで見ると、S0 の MAE は 3.23〜3.39）。
- 地点は青森1地点、冬は11〜3月だけ。ほかの地点・季節で同じ結果になるかは分からない。

## ファイル

- `fetch_jma_long.py`: 気象庁の日別データを2016-01〜2026-08にそろえる（`data/long/`）
- `fetch_openmeteo.py`: Open-Meteo から GSM・MSM の毎時値を取得（`data/openmeteo/`）
- `common.py`: データセット（観測＋数値予報の特徴量）、S0/SA/SB の列、分割、CV、モデル、探索範囲。前回の `04-snow-model/common.py` を読み込んで再利用
- `check_gsm_native_hours.py`: GSM・MSM の本来の時刻と補間の確認
- `test_no_leak.py`: 数値予報の特徴量に未来の値が混ざっていないことのテスト
- `tune.py`: Optuna によるチューニング（学習データ内のCVのみ）
- `run_tune_all.sh`: 45件（3セット×5手法×3 seed）を9件ずつ並列で実行
- `evaluate.py`: 評価データでの最終評価、基準、過学習のギャップ、ブートストラップ、seed違い、係数、permutation importance
- `check_logreg_weight_range.py`: ロジスティック回帰のクラス重みの探索範囲を広げた確認（CVのみ）
- `compare_before_after.py`: 修正前（`results_v1_before_fix/`）と修正後の比較
- `plot.py`: 図の作成
- `results/aomori/metrics_reg.csv`, `results/aomori/metrics_clf.csv`: 回帰・分類の全指標（seed 42、基準を含む。学習データでの成績、「常に0」比も含む）
- `results/aomori/predictions_eval.csv`: 評価データの日ごとの実測・予測（回帰の予測と分類の確率）
- `results/aomori/heavy_days_eval.csv`: 評価データの大雪日と、SAの回帰の予測が15cm以上だった日
- `results/aomori/bootstrap.csv`: 差の95%区間
- `results/aomori/seed_robustness.csv`, `results/aomori/seed_set_differences.csv`: seed ごとの結果と、特徴量セットの差
- `results/aomori/best/*.json`, `results/aomori/trials/*.csv`: 各チューニングの最良パラメータ・CVスコア・全試行
- `results/aomori/linear_coefficients.csv`: Ridge回帰・ロジスティック回帰の標準化係数
- `results/aomori/permutation_groups.csv`, `results/aomori/permutation_features.csv`: permutation importance（グループ単位・列単位）
- `results/aomori/compare_before_after.csv`: 修正前後の主な数字
- `results_v1_before_fix/`: 修正前（GSMの補間値を使っていた版）の結果・図・ログ。記事には使わない
- `images/aomori/fig1-eval-mae.png`: 特徴量セット×手法の評価MAEと基準
- `images/aomori/fig2-eval-heavy-ap.png`: 大雪の分類の評価AP
- `images/aomori/fig3-group-importance-SA.png`: SA のグループ単位の permutation importance
- `images/aomori/fig4-eval-timeseries.png`: 評価データの実測と S0/SA/SB の予測（勾配ブースティング）
- `logs/aomori/`（青森の評価・チューニング・テストのログ）と `logs/`（データ取得・GSMの確認のログ）: 実行ログ（ログにはローカルの絶対パスを出さない。`fetch_jma_long.log` は最初の実行（67か月を取得）のログで、保存先の表示だけを手で相対パスに書き換えた。いま再実行すると取得済みのため「取得 0か月」と出る）
